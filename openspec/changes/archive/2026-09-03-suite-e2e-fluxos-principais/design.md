## Context

A PoC existente (`AncorAI/e2e/busca-local.spec.ts`) provou que o Playwright dirige a janela Electron real via `_electron.launch()`, e estabeleceu dois precedentes que esta mudança mantém: (1) semear o banco NeDB local via `banco/repositorio.ts` em vez de escrever o `.db` na mão, e (2) isolar `userData` via a env var `ANCORAI_E2E_USER_DATA_DIR`, lida em `src/main/index.ts` antes de `inicializarCofre`/`abrirBanco`. Ver proposal.md - Why.

O ponto novo é que os fluxos restantes não são todos "puramente locais" como a busca sobre snapshot: alguns exigem rede (GitHub e/ou Gemini) para acontecer de verdade. Pesquisa no código (`src/main/fontes/github.ts`, `src/main/llm/gemini.ts`, `src/main/llm/resumos.ts`, `src/main/conteudo/ingestao.ts`) mostrou:

- `github.ts` e `gemini.ts` usam `fetch` nativo contra URLs `BASE` hardcoded (`https://api.github.com` e `https://generativelanguage.googleapis.com/v1beta`), sem nenhum ponto de injeção hoje.
- Testes Vitest mockam essas chamadas com `vi.stubGlobal('fetch', ...)` — inaplicável aqui, porque o processo que faz as chamadas é o processo **main real do Electron**, lançado pelo Playwright como um binário, não código rodando sob o test runner.
- `resumos.ts` - `prepararConteudo`/`resumoDoDocumento` chamam `estaVigente(registro, documento)` (`conteudo/ingestao.ts:76-89`), que devolve `true` sem checar nada externo quando `documento.versaoConteudo` é `undefined` e já existe um `RegistroConteudo` local. Ou seja: **semeando o texto do documento diretamente via `gravarConteudo()`** (sem popular `versaoConteudo` no `Documento` do inventário), o fluxo de resumo nunca precisa tocar o GitHub — só o Gemini, para gerar o resumo em si.
- `relacoes/pilha.ts` opera inteiramente sobre rótulos (`assuntos`/`categoria`) já gravados no NeDB — nenhuma chamada de rede em ponto algum.
- `documento:abrir` (`ipc.ts:110`) chama `shell.openExternal(documento.link)` diretamente — não há como interceptar isso de dentro do Playwright sem modificar o processo main, e fazer isso abriria de fato um navegador externo durante o teste.
- A varredura de sincronização (`conteudo/ingestao.ts` - `varrerAcervo`) é o único fluxo que **precisa** exercitar `github.ts` de ponta a ponta: `buscarDocumentos` (repos + árvore), `autoriaDoArquivo` (commits por caminho) e a obtenção de conteúdo (blob) para os documentos do inventário.
- Validação de credencial do GitHub (`GET /user`) e validação/uso da chave do Gemini (`GET /models`, `POST /models/{modelo}:generateContent`) são as únicas chamadas de rede do fluxo de configuração.

## Goals / Non-Goals

**Goals:**
- Cobrir, com um teste E2E cada, os fluxos: configuração de credenciais (GitHub + Gemini), sincronização do acervo, resumo por IA (incluindo consentimento), documentos relacionados, e abertura de documento — complementando a busca já coberta pela PoC.
- Cobrir cada filtro de `Filtros.tsx` (buscar no conteúdo, extensão, período, ordenação) com um teste isolado, sobre um snapshot local próprio.
- Nenhum teste desta suíte deve depender de rede real, de uma credencial real, ou de um keyring do SO funcionando de forma imprevisível (ver Risco de `safeStorage` abaixo).
- Manter o app de produção praticamente intocado, seguindo o mesmo padrão de impacto mínimo da PoC (um ponto de injeção gated por env var de teste).
- Reduzir duplicação entre os novos arquivos de teste com fixtures/helpers compartilhados, já que cinco fluxos novos repetiriam a mesma lógica de setup se copiados da PoC.

**Non-Goals:**
- Não é objetivo migrar `busca-local.spec.ts` para as novas fixtures — ele já passa e mexer nele é risco desnecessário para o escopo desta mudança.
- Não é objetivo implementar um mock HTTP genérico/reutilizável para outros propósitos além desta suíte.
- Não é objetivo cobrir todos os endpoints de `github.ts` (ex.: paginação de `/user/repos` além de uma página, ou o caminho de `truncated: true` na árvore) — só o necessário para cada fluxo completar de ponta a ponta.
- Não é objetivo configurar CI.

## Decisions

**1. Ponto de injeção de endpoint via env vars, seguindo o mesmo padrão de `ANCORAI_E2E_USER_DATA_DIR`.**
`src/main/fontes/github.ts` e `src/main/llm/gemini.ts` passam a resolver `BASE` como `process.env['ANCORAI_E2E_GITHUB_BASE_URL'] || 'https://api.github.com'` e `process.env['ANCORAI_E2E_GEMINI_BASE_URL'] || 'https://generativelanguage.googleapis.com/v1beta'`, respectivamente — uma linha por arquivo, lida no carregamento do módulo. Fora do cenário de teste (env var ausente), o comportamento é idêntico ao atual; nenhum outro ponto do app muda.
*Alternativa descartada*: interceptar `fetch` em nível de processo (ex.: sobrescrever `global.fetch` a partir de um script injetado no `_electron.launch()`). Rejeitada porque exigiria carregar código extra dentro do processo Electron antes do bootstrap da aplicação (não suportado de forma simples pelo Playwright para Electron), enquanto uma env var lida no próprio bootstrap já é o mecanismo comprovado pela PoC.

**2. Servidor HTTP mock local, subido por teste via `node:http`, um por fluxo que precisa de rede.**
Cada spec que precisa de rede sobe seu próprio servidor mock (porta efêmera, `listen(0)`) com só as rotas que aquele fluxo exercita, e passa as duas env vars do item 1 apontando para ele em `electron.launch({ env: {...} })`. Rotas exatas por fluxo, com base no contrato real extraído de `github.ts`/`gemini.ts`:
   - **Configuração de credenciais**: `GET /user` → `{ login }` (GitHub); `GET /models?pageSize=200` → `{ models: [{ name: 'models/gemini-3.1-flash', supportedGenerationMethods: ['generateContent'] }] }` (Gemini).
   - **Sincronização do acervo**: `GET /user/repos?...` → um repositório de exemplo; `GET /repos/{full_name}/git/trees/{branch}?recursive=1` → árvore com 1-2 blobs; `GET /repos/{full_name}/commits?path=...&per_page=1` → autoria de exemplo; `GET /repos/{full_name}/git/blobs/{sha}` (`Accept: application/vnd.github.raw`) → bytes de texto simples.
   - **Resumo por IA**: só `POST /models/{modelo}:generateContent` → envelope `{ candidates: [{ content: { parts: [{ text: '<JSON stringificado com resumo/categoria/assuntos/destaques>' }] } }] }`, e `GET /models?pageSize=200` (a resolução do modelo consulta o catálogo antes de gerar). Nenhum endpoint do GitHub é necessário (ver item 3).
   - **Filtros de busca**: nenhum mock. Descoberto durante a implementação que `aoAlterarFiltros` em `App.tsx` só reconsulta automaticamente ao trocar extensão/período quando `temCredencial` é verdadeiro — mas o clique/preenchimento do controle sempre atualiza o estado local dos filtros, mesmo sem credencial, e reenviar o formulário de busca (`aoSubmeter`, que nunca checa `temCredencial`) consulta o snapshot com esse estado já atualizado. O teste ajusta o filtro pela UI e clica em "Buscar" de novo para aplicá-lo, em vez de depender da reconsulta automática — evitando por completo a necessidade de uma credencial validada (e, com ela, o bloqueio de `safeStorage` — ver Risco abaixo).
   - **Documentos relacionados / abertura de documento**: nenhum servidor mock — fluxos puramente locais.
*Alternativa descartada*: um único servidor mock global compartilhado entre todos os specs. Rejeitada porque cada fluxo precisa de dados de resposta diferentes (ex.: o resumo gerado varia por teste) e um servidor compartilhado com estado mutável entre testes é fonte de flakiness; um servidor por teste, subido em `beforeEach`/`afterEach`, mantém cada teste isolado e determinístico.

**3. Fluxo de resumo por IA e de documentos relacionados semeiam texto/resumo diretamente no NeDB, sem tocar `github.ts`.**
Usando `gravarConteudo()` para popular `RegistroConteudo.texto`/`estado: 'extraido'` (resumo) e `gravarConteudo()` + `gravarResumo()` para popular resumo/assuntos/categoria já prontos (relacionados), sem preencher `versaoConteudo` no `Documento` semeado — o que faz `estaVigente()` (`conteudo/ingestao.ts:76-89`) considerar o texto local já válido, sem checar o GitHub. Isso mantém esses dois testes menores e mais estáveis (uma dependência de rede a menos cada), e é consistente com o espírito da PoC de evitar mock de rede onde o caminho testado não o exige.
*Alternativa descartada*: exercitar a ingestão completa via GitHub mock também para esses dois fluxos. Rejeitada por escopo — o que esses testes validam é o comportamento do painel de resumo e da pilha de relacionados, não a ingestão (que já é o foco do teste de sincronização).

**4. Fluxo de abertura de documento: `shell.openExternal` é desligado sob a suíte E2E, e o registro de acesso é verificado por leitura direta do NeDB, não pela UI.**
Revisado durante a implementação: `documentosAcessados`/`listarAcessados` (`documento:acessados`) não têm **nenhum** consumidor no renderer hoje — `grep` em `src/renderer/` não encontra uma única referência, e a spec `busca-documentos` só exige que o acesso seja registrado, não que apareça em algum lugar da tela. A ideia original desta decisão (verificar via "lista de recentes" na UI) não correspondia a nada que exista. Ao mesmo tempo, deixar `shell.openExternal` disparar de verdade abriria um navegador real nesta máquina a cada execução da suíte — um efeito colateral inaceitável para um teste automatizado, pior do que se pensava originalmente (não é só "não deveria", é um incômodo real e repetido). Por isso `documento:abrir` (`ipc.ts:108-114`) passou a pular o `shell.openExternal` quando `ANCORAI_E2E_USER_DATA_DIR` está definida — a mesma env var que toda execução desta suíte já define para isolar `userData`, sem introduzir uma nova. O teste clica em "Abrir em GitHub"/"Abrir documento no GitHub" e verifica o registro via `listarAcessados()` chamado diretamente do processo de teste (mesmo padrão de `semear.ts`).
*Alternativa descartada (mantida do design original)*: verificar via alguma reconsulta na UI. Descartada porque não há UI alguma para isso — não é uma escolha de design, é a ausência de um recurso a verificar.

**5a. Credenciais são semeadas pela UI de configurações contra o mock, nunca por import direto de `credenciais/cofre.ts` no processo de teste.**
`cofre.ts` importa `safeStorage` de `'electron'` no topo do arquivo — módulo que só resolve para a API real dentro do processo Electron (`main`); importado do processo de teste do Playwright (Node puro, fora do binário Electron), `safeStorage` não é a API esperada, e chamar `cofre.definir()`/`cofre.obter()` de lá falha. `repositorio.ts`, por não ter essa dependência, continua seguro para semeadura direta (documentos, texto, resumo). Qualquer teste que precise de uma credencial válida no cofre (sincronização, resumo por IA) a obtém passando pela tela de configurações real no início do teste — preenchendo o campo e salvando contra o servidor mock — em vez de um atalho fora da UI.
*Alternativa descartada*: um pequeno script auxiliar rodando dentro do processo Electron antes do teste (via `_electron.launch()` com um preload de setup) para gravar a credencial sem passar pela UI. Rejeitada por adicionar complexidade e mais um "modo de teste" só para economizar alguns cliques que a própria tela de configurações já exercita e valida.

**5. Fixtures compartilhadas em `AncorAI/e2e/apoio/`, mas sem page objects.**
Um helper `lancarApp()` (função simples, não um fixture `test.extend` — a variedade de combinações de seed/mock por teste não se prestava bem a um fixture rígido) encapsula o lançamento do app e devolve `{ janela, diretorioDados, fechar() }`. Um segundo helper por área (`servidorMockGithub.ts`, `servidorMockGemini.ts`, sobre uma base comum em `servidorHttp.ts`) expõe uma função `subirServidorX(config)` que sobe o `node:http` server com handlers configuráveis por teste. `semear.ts` existente é estendido com novas funções (não reescrito) para os casos de uso de texto/resumo pré-gravado. Isso é uma abstração mínima — evita duplicar boilerplate de `beforeEach`/`afterEach` em 6 arquivos novos — mas não introduz page objects (seletores continuam inline em cada teste, como na PoC), porque a suíte ainda é pequena o suficiente para não justificar essa camada extra.
*Alternativa descartada*: repetir o boilerplate de `busca-local.spec.ts` em cada novo arquivo, sem fixtures. Rejeitada porque, com 6 fluxos novos (vs. 1 da PoC), a duplicação de setup passaria a ser o principal risco de manutenção da suíte.

**5b. `lancarApp()` gera o app via `child_process.spawn` + `chromium.connectOverCDP`, não `_electron.launch()` do Playwright — descoberta feita ao implementar o grupo de credenciais (ver Risco de `safeStorage`, resolvido abaixo).**
`_electron.launch()` é o mecanismo que a PoC usa e que a proposta original desta mudança assumia reaproveitar. Ele falhou de forma determinística nesta máquina: `safeStorage.isEncryptionAvailable()` volta sempre `false` (`backend: basic_text`) para um processo que ele lança, mesmo com os mesmos argumentos/ambiente que, lançados por um `child_process.spawn` comum, resultam em `true`/`gnome_libsecret` — o mesmo princípio do wrapper local `ancorai-dev`, que o usuário confirmou funcionar nesta máquina (`unset ELECTRON_RUN_AS_NODE` + execução direta do binário, sem infraestrutura de automação no caminho de inicialização). `lancarApp()` passou a: (1) encontrar uma porta livre; (2) `spawn('./node_modules/.bin/electron', ['--ozone-platform=x11', '--remote-debugging-port=<porta>', 'out/main/index.js'], { env })`, com `ELECTRON_RUN_AS_NODE` removido do ambiente herdado, como o wrapper já fazia; (3) esperar o endpoint `/json/version` da porta responder; (4) `chromium.connectOverCDP('http://127.0.0.1:<porta>')` e obter a primeira página do primeiro contexto como `janela`. Verificado ponta a ponta: o fluxo de configuração de credenciais agora grava e valida um token de verdade (`getByText('Conectada')` fica visível), o que nunca acontecia sob `_electron.launch()`.
Efeito colateral aceito: `ElectronApplication.evaluate()` (execução no processo main) deixa de existir — nenhum teste planejado precisa disso; só os probes de diagnóstico usados para isolar o problema, descartados depois.

Um segundo bug, também pré-existente e também nunca antes exercitado (inclusive por `_electron.launch()`), apareceu ao escrever o teste de resumo por IA: apontar o Electron direto para o arquivo `out/main/index.js` (como a PoC já fazia) faz `app.getAppPath()` resolver para `out/main/`, não a raiz do projeto — sem `package.json` ali para ancorar a resolução. `lerInstrucao()` (`llm/instrucao.ts`) nunca encontra `instrucoes/resumo.md` nesse caso, e todo resumo falha com uma mensagem genérica em vez do motivo real. `lancarApp()` passou a apontar para o diretório do projeto (`.`) em vez do arquivo — o Electron usa o campo `main` do `package.json` para achar o mesmo `out/main/index.js`, e `getAppPath()` passa a resolver corretamente. Verificado: os dois testes de resumo (sucesso e cota excedida) passam depois da correção, e os grupos anteriores (filtros, credenciais, sincronização) continuam passando juntos.
*Alternativa descartada*: manter `_electron.launch()` e aceitar que os testes de configuração/sincronização/resumo só exercitem o braço de "credencial indisponível". Rejeitada a pedido do usuário: o objetivo explícito é verificar o caminho feliz desses fluxos nesta máquina, não documentar uma limitação em torno dela.
*Alternativa descartada*: investigar a causa raiz dentro do Playwright/Chromium antes de prosseguir. Descartada por custo/benefício incerto depois que o `child_process.spawn` já resolveu o problema de forma direta e verificável.

**6. Fixtures de filtros estendem `semear.ts` com um conjunto de documentos deliberadamente heterogêneo, apartado do par usado pela PoC.**
Os dois documentos de `semear.ts` (`TERMO_DISTINTIVO`/`NOME_DOCUMENTO_ALVO`) servem só ao teste de busca da PoC e não têm variação de extensão nem datas distantes o bastante para exercitar período/extensão/ordenação de forma inequívoca. Uma nova função `semearParaFiltros(diretorioDados)` insere um conjunto próprio (extensões distintas, datas espaçadas, e ao menos um documento cujo termo só aparece no *conteúdo*, não no nome, para o teste de "Buscar no conteúdo") — sem alterar o par existente, para não arriscar o teste da PoC.
*Alternativa descartada*: reaproveitar/ampliar o array `DOCUMENTOS` já existente em `semear.ts`. Rejeitada porque `busca-local.spec.ts` depende de propriedades específicas desse conjunto (contagem, nomes exatos) e ampliá-lo é risco de regressão no teste que já passa, para um ganho de conveniência pequeno.

**7. `semearComTexto`/`semearComResumo` acrescentam ao inventário em vez de substituí-lo, e o consentimento é pedido mesmo para resumo já gravado.**
Dois problemas descobertos ao escrever o teste de documentos relacionados (que semeia 3 documentos com chamadas separadas): (a) `sincronizarInventario()` (`repositorio.ts`) remove qualquer documento fora da lista recebida — chamá-la uma vez por documento apagava os anteriores. `semear.ts` passou a ler o inventário existente (`inventarioSincronizado()`) e uni-lo ao novo documento antes de gravar (`sincronizarAcrescentando`), preservando as chamadas anteriores. (b) `App.tsx` calcula `motivo` do painel como `'sem-consentimento'` sempre que `!statusLLM.consentido`, **independente** de já haver um `resumo` carregado — então mesmo um resumo já gravado (`resumoGravado`, sem gerar nada) fica atrás do bloco de consentimento. Os testes que dependem de um resumo pré-gravado (relacionados) passaram a clicar em "Permitir e gerar resumos" antes de checar o painel, mesmo sem precisar gerar nada de novo (`focarDocumento` refeito após o consentimento encontra o resumo já gravado pela mesma via rápida).

## Risks / Trade-offs

- **[Risco RESOLVIDO] `safeStorage.isEncryptionAvailable()` era sempre `false` para o app lançado via `_electron.launch()` nesta máquina, fazendo `cofre.definir()` lançar erro em vez de gravar a credencial.** Isolado durante a implementação: o mesmo binário, com o mesmo `--ozone-platform=x11` e o mesmo ambiente (`DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`), retornava `isEncryptionAvailable: true` / `backend: gnome_libsecret` quando lançado diretamente (`./node_modules/.bin/electron ...`), mas `false` / `backend: basic_text` quando lançado por `_electron.launch()` do Playwright — mesmo replicando manualmente os mesmos argumentos de linha de comando. A causa exata (dentro do Playwright/Chromium) não foi isolada, mas o usuário confirmou que `ancorai-dev` (um `child_process` comum, sem `_electron.launch()`) inicia o app corretamente nesta máquina — o mesmo princípio adotado por `lancarApp()` (Decisão 5b), que resolveu o problema: o fluxo de configuração de credenciais grava e valida um token de verdade de ponta a ponta, verificado com 3 execuções determinísticas.
- **[Risco] O mock de sincronização precisa reproduzir uma árvore/commits/blob GitHub minimamente coerentes; qualquer divergência do contrato real (`github.ts`) quebra o teste de forma pouco óbvia.** → Mitigação: as rotas e formatos de resposta usados pelo mock foram extraídos diretamente do código-fonte de `github.ts` (não documentação externa) durante o design desta mudança; a implementação (tasks.md) deve validar cada rota contra o parsing real antes de dar o fluxo por coberto.
- **[Risco] Um servidor `node:http` por teste pode vazar (não fechar) se um teste falhar no meio.** → Mitigação: fechamento do servidor mock no `afterEach`/`finally`, com `server.close()` chamado incondicionalmente, mesmo em caso de falha da asserção — mesmo padrão que a PoC já usa para `app.close()`/`rmSync`.
- **[Risco CONFIRMADO E CORRIGIDO] `fullyParallel: false` não impede o Playwright de usar múltiplos workers entre arquivos diferentes — só serializa dentro de um mesmo arquivo.** Rodar a suíte completa expôs uma corrida real: dois workers resolvendo a mesma porta livre (`portaLivre()` em `lancarApp.ts`) entre o instante em que o socket de sondagem fecha e o Electron efetivamente liga naquela porta, derrubando um teste de filtros de forma não determinística. → Correção: `workers: 1` em `playwright.config.ts`, tornando a suíte inteira serial. Verificado com 3 execuções completas (19/19) sem falhas depois da correção.
- **[Trade-off] A suíte fica mais lenta que a PoC** (mais processos Electron lançados, mais servidores HTTP locais, agora serializados por `workers: 1`) — cerca de 22s para os 19 testes nesta máquina. Aceitável dado o volume de testes desta suíte.
- **[Trade-off] Cobertura de `github.ts` no fluxo de sincronização é parcial** (uma página de repositórios, uma árvore pequena, sem caso de `truncated: true` ou paginação) — deliberado, ver Non-Goals.
